# IEUM WAVE 구현·검증 기록

## 공통 네이티브 호스트 통합 · 2026-11-04 UTC

`NativeAudioEngine` → Electron 서비스 → 실제 `garak-audio-host` → 공통 `RenderEngine` → WAVE DSP 연결을 추가했습니다. WASAPI·ASIO·Core Audio 장치 어댑터는 이 공통 렌더러의 출력을 사용합니다.

위 Linux 검증에서 실제 DSP 오디오 샘플과 PCM WAV를 확인했습니다. 호스트 통합 검사는 **명시적인 테스트 클록**을 사용합니다. Chromium UI 검증은 실제 앱과 네이티브 서비스를 명시적인 QA 전송 어댑터로 연결한 것이며, 실제 Electron 창이나 물리 WASAPI·ASIO·Core Audio endpoint의 소리, 장치별 안정성 및 왕복 지연을 측정했다는 뜻은 아닙니다. 설치 앱 smoke에도 실제 편집기 건반 → IPC → native meter, preset 적용, 편집기 닫기 후 note release와 MIDI 가져오기 검사를 추가했습니다.

검사일: **2026-11-04 UTC**. 아래 기록의 기준 브랜치는 `main`의 `9c4a1f3d3358406b7387433ce7999624a8dfb512`입니다. 당시에는 프로젝트에 연결한 음색 편집기와 독립 C++ 음원 모듈을 검증했으며, 공통 호스트 연결은 위 후속 통합에서 추가했습니다.

웹 빌드는 기존 메인 번들의 500 kB 초과 경고를 출력합니다. 신디사이저 편집기는 별도 청크로 분리되어 있으며, 이 변경에서 번들 경고를 숨기거나 CI 설정을 바꾸지 않았습니다.

Windows CI에서 생성 파일의 CRLF 줄바꿈을 내용 변경으로 판단하는 검사 오류가 발견됐습니다. 같은 CRLF 파일을 임시 디렉터리에 구성해 수정 전 실패를 재현한 뒤, 비교 단계에서만 CRLF를 LF로 정규화했습니다. 실제 fingerprint를 바꾸면 TS와 C++ 두 생성 파일 모두 계속 실패하고, CRLF manifest로 재생성한 결과도 기존 LF 출력과 완전히 같습니다. 공개 fingerprint `4061721317`와 음원·바이너리 전송 내용은 변경하지 않았습니다. 위 940개는 이 회귀를 포함한 최종 Linux 개발 환경 검사 수입니다.

### 프로젝트 보존과 연결 실패 처리

사용자 파형, LFO 곡선, 변조 연결과 메타데이터가 실제 프로젝트 번들로 왕복합니다. 트랙 복제 후 수정이 원본에 반영되지 않고, 프리셋 변경 및 다른 악기로 전환한 편집도 같은 프로젝트 Undo/Redo로 되돌립니다. MCP의 스칼라 편집은 구조 상태를 보존합니다.

브라우저 엔진에서 새 악기를 기존 건반 소리로 재생하는 fallback을 막았습니다. 오디오 장치 준비를 기다리는 동안 프로젝트가 바뀌는 경우와, 대기 중인 트랙 미리 듣기가 다른 악기로 바뀌는 경우도 회귀 검사했습니다. 가시 구간 밖으로 트리밍된 음표, 음역·세기 제한, 뮤트·솔로·볼륨, 반복·딜레이를 고려해 실제 재생할 네이티브 음표가 있을 때만 장치 연결 요구를 표시합니다.

네이티브 타임라인 준비 함수는 새 악기를 `native-wavetable`로 구별하고 검증된 전체 패치를 복사합니다. 실제 장치 호스트는 이 소스를 새 DSP 모듈에 연결해야 합니다.

### 네이티브 동작

검사는 sample-offset 173의 정확한 발음 시작, 블록 분할을 달리해도 같은 샘플이 나오는 결정성, sustain/release, 반복 음표와 voice stealing, 18개 변조 대상의 실제 소리 변화, LFO의 BPM/Hz와 transport/retrigger 구분을 포함합니다.

누른 음을 유지한 채 스칼라·LFO·파형을 수정하고, 사용자 뱅크 4만 있는 패치에서 뱅크 5만 있는 패치로 원자적으로 교체하는 경로를 검사했습니다. 콜백 및 실시간 패치/파형 교체 경로의 **heap allocation은 0회**였습니다. 긴 무음 이후 딜레이 상태가 극소수에 남지 않고 0으로 돌아오는 검사도 포함합니다.

## WAV 확인 조건

실제 TypeScript factory preset과 사용자 파형을 `encodeWavetablePatch()`로 인코딩한 뒤 C++ 렌더러에 전달했습니다. 각 파일은 **48 kHz, 스테레오 float32, 12초**, MIDI 음표 **60·64·67을 동시에 3초간**, velocity **0.8**, BPM **120**, seed **123**으로 생성했습니다.

- 11개 WAV 헤더와 실제 샘플 배열을 다시 읽었습니다. 모든 샘플이 유한한 수였습니다.
- 파일별 출력 피크는 **0.16423–0.43063**이었습니다.
- 렌더러의 출력 천장 접근 기준인 `abs(sample) > 0.939`에 해당하는 샘플은 **0개**였습니다.
- 모든 파일의 마지막 active voice 수는 **0**이었습니다. 긴 release를 가진 패치도 종료를 확인했습니다.

이 결과는 해당 프리셋과 검사 조건에 대한 것입니다. 모든 가능한 사용자 패치의 음량·앨리어싱·음악적 품질을 보장하지 않습니다.

## 처리 시간과 남은 성능 범위

환경: Linux 개발 컨테이너, AMD EPYC 9V74로 표시되는 CPU, GNU C++ 13, C++17 Release. 장치 드라이버의 실시간 오디오 콜백이 아닌 일반 프로세스입니다.

아래는 다른 빌드·브라우저 검사가 끝난 뒤 루트에서 실행한 최종 소스의 독립 측정입니다. 조건은 **16 voices × 3 OSC × 7 unison + 16 routes + 두 필터 + 모든 내부 FX**, **64-frame 블록 1,024개**입니다. 단위는 ms입니다.

| 샘플레이트 | 한 블록 시간 예산 | p50 처리 시간 | p95 | p99 | 관측한 시간 초과 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 44.1 kHz | 1.451 | 0.595 | 0.949 | 2.544 | 24 / 1,024 |
| 48 kHz | 1.333 | 0.639 | 0.778 | 1.084 | 4 / 1,024 |
| 96 kHz | 0.667 | 0.550 | 0.836 | 1.133 | 181 / 1,024 |

같은 소스의 별도 개발 실행에서는 48 kHz p99 0.767 ms, 초과 0/1,024가 관측됐습니다. 반대로 전체 JS 테스트·빌드와 동시에 실행한 부하 조건에서는 48 kHz p99가 약 8.80 ms로 늘었습니다. 이 차이는 이 환경의 스케줄링 영향을 보여주며, 가장 좋은 실행만으로 무중단 동작을 주장할 수 없습니다.

16×3×7 + FX 지속음 1초의 독립 렌더는 **0.309초, 약 3.24배 실시간**이었습니다. 이 평균 렌더 처리율을 오디오 입출력 레이턴시로 해석하면 안 됩니다.

**48 kHz를 초기 호스트 통합의 기준으로 삼되 실제 장치에서 다시 측정해야 합니다. 96 kHz의 최대 조합은 현재 구현·시험 환경에서 충분한 여유가 없습니다.** 보이스 stealing의 임시 fading voice와 파형 교차 전환은 지속음 조건보다 추가 부하를 만듭니다. 이 최악 조건 및 여러 트랙을 함께 쓰는 경우도 장치 통합 후 검사해야 합니다.

정지 saw 파형의 특정 주기 시험에서는 비고조파 잔여 에너지가 약 **−145.70 dB**, 비교용 naive saw는 **−13.89 dB**였습니다. 이는 대역 제한 표의 해당 정지 시험 결과입니다. 빠른 변조·drive·전체 악기의 무앨리어싱이나 상용 악기와 동등한 음질을 의미하지 않습니다.

## 아직 확인하지 않은 항목

- ASIO/WASAPI/Core Audio 장치를 사용하는 실제 가락이음 네이티브 호스트 연결
- Windows/Apple Silicon 네이티브 컴파일과 실시간 실행
- 실제 MIDI 장치부터 오디오 출력까지의 레이턴시, 장치 해제/재연결, 장시간 연주
- 여러 신디사이저·앰프·트랙을 함께 사용하는 전체 그래프의 CPU 및 드롭아웃
- 상용 신디사이저와의 청취 비교

## 재현 명령

```sh
pnpm test
pnpm build
pnpm mcp:build
pnpm desktop:compile
pnpm wavetable:schema
pnpm wavetable:build
pnpm wavetable:test
pnpm wavetable:fixtures
pnpm wavetable:smoke
```

수치 로그가 필요하면 `build/native/wavetable-synth/ieum-wave-tests`를 직접 실행합니다. sanitizer 검사는 별도 CMake 빌드 디렉터리에서 `-DIEUM_WAVE_SANITIZE=ON`으로 구성합니다. 이 환경에서는 `ASAN_OPTIONS=detect_leaks=0`을 사용했습니다.

원본 API와 준비된 파형의 소유권 규칙은 [네이티브 README](../native/devices/wavetable-synth/README.md), 사용자 조작과 호스트 연결 안내는 [IEUM WAVE 사용법](IEUM_WAVE.md)에 있습니다.
