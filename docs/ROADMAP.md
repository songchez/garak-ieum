# 가락이음 로드맵

**현재 버전은 0.1.1 개발 프리뷰입니다.** 다음은 개발 방향과 완료 기준이며, 구현 완료 목록이나 출시 일정의 약속이 아닙니다. 현재 사용할 수 있는 기능은 [README](../README.md), 실제 실행 구조는 [아키텍처](ARCHITECTURE.md)에 기록합니다.

## 버전 방향

| 단계 | 목표 | 현재 상태 |
| --- | --- | --- |
| 0.1.0 | 편집부터 재생·저장·출력까지 이어지는 실행 가능한 초기 버전 | 구현 기반 |
| 0.1.1 | GPL-3.0-only 전환, 배포 고지와 해당 커밋의 소스 묶음 | 현재 코드 |
| 1.0 | 일상적인 곡 작업에 사용할 웹 편집기 + 오디오 엔진 | 개발 중 |
| 2.0 | 웹 기술로 만든 UI + 로컬 네이티브 호스트 + 기존 플러그인 | 계획 단계 |

이 구분에서 1.0은 외부 네이티브 VST 호환성을 포함하지 않습니다. 2.0은 현재 웹 엔진에 기존 가상악기 파일을 단순 업로드하는 방식이 아니라, 설치된 플러그인을 실행할 로컬 호스트를 추가하는 단계입니다.

## 0.1.0에서 만들어진 기반

오디오·MIDI 클립을 편집하고, 내장 합성 악기와 기본 효과를 실제 재생하며, 마이크 녹음·원본 오디오 보관·프로젝트 파일 교환·WAV 출력으로 이어지는 기본 경로가 있습니다. React UI와 엔진 서비스를 나누고, 오디오 그래프를 실시간·오프라인 출력에 공통 사용합니다.

오디오 설정에는 입력 장치와 조건부 출력 선택, 지연·렌더 블록 요청, 전역 모니터링, 입력/출력 테스트, 실제 상태 진단, 수동 ms 녹음 정렬을 연결했습니다. 프로젝트 샘플레이트는 저장·Undo/Redo·엔진·PCM 16-bit WAV에 반영합니다. 하드웨어 드라이버 제어나 실제 인터페이스 검증까지 완료했다는 뜻은 아니며, 범위와 검증 상태는 [구현 상태](IMPLEMENTATION_STATUS.md)와 [오디오 설정 벤치마크](AUDIO_SETTINGS_BENCHMARK.md)를 따릅니다.

이 단계는 제품 방향을 직접 써보며 판단하는 기반입니다. 장시간 녹음, 대규모 편곡, 여러 브라우저와 장치에서의 일관성은 후속 검증 대상입니다.

## 1.0 정식 버전 전 우선 작업

### 디바이스 모듈화·음표 단위 오디오 피치 편집

EQ·필터·컴프레서·드라이브·딜레이·리버브의 정의·DSP·잔향 계산을 독립 모듈로 분리했습니다. 공통 등록부가 UI·검증·MCP의 기존 이펙트 목록을 제공합니다. 합성 악기 분리와 사용자 정의 UI 등록 계약은 남아 있습니다.

현재 피치 편집기는 디바이스 랙에서 여는 **리전 처리 모듈**입니다. 원본·고정 분석·편집 명세·렌더 자산을 분리하고, 단선율 음표 분석·이동·분할/합치기·실제 재합성·프로젝트 Undo·저장·재생/출력을 연결했습니다. 선택 음표의 반음계·장음계·자연 단음계 보정과 0–100% 강도, 기본 꺼짐의 실험적 포먼트 보존·음표별 ±1200 ct 이동도 구현했습니다. 보정 옵션은 프로젝트 ID별 세션 도구 설정이며, 버튼을 눌러야 음표가 변경됩니다. 피치 문서는 v2로 이전하되 프로젝트 스키마 3과 기존 렌더 자산을 유지합니다. [피치 편집기 안내](PITCH_EDITOR.md)에 현재 제한과 사용법을 기록합니다.

다음은 실제 보컬·독주 청음과 브라우저 조작/복원 회귀 검증, 포먼트 처리의 음색·음량 품질 개선, 드리프트/비브라토·타이밍 편집, 피치 MCP 명령입니다. 포먼트 보존과 이동은 아직 실험 기능이며, 내부 보정량이 ±1200 ct를 넘는 조합은 적용하지 않습니다. 다성 악기 개별 음 분리와 멀티트랙·배음 도구는 별도의 연구·평가 단계입니다. [전체 설계](PITCH_DEVICE_DESIGN.md)의 기능 목록과 Melodyne 수준의 음질 달성은 별도로 평가합니다.

**완료 기준:** 대표 음원에서 원본 보존·음높이·길이·경계 음질을 확인하고 실제 브라우저의 재생·Undo·저장/복원·WAV 출력이 일치해야 합니다. 자동 테스트 통과를 청음 검증 완료로 대신하지 않습니다.

### AI 편집·코드 작곡

목표는 사람이 자연어로 편집·믹싱을 지시하고, AI가 사람이 이어서 편집할 수 있는 음악 초안을 만드는 것입니다. 음악적 판단과 최종 청음은 사람의 작업 흐름에 포함합니다.

현재 첫 단계로 공통 `ProjectSession`, revision·원자성·중복 요청 보호, 로컬 MCP의 상태/카탈로그/지원 범위 조회와 트랙·리전·믹싱 19개 명령을 연결했습니다. 명시적인 MIDI 이벤트로 만든 초안은 일반 리전이며 피아노롤에서 수정할 수 있습니다. [MCP](MCP.md)의 지원 목록 밖 기능을 이미 자동화된 것으로 보지 않습니다.

다음 단계는 실제 UI에 구현된 편집 명령을 차례로 노출하고, 원본/재생 음표 조회·범위 렌더·객관적인 오디오 측정과 실행 결과를 연결하는 것입니다. 아직 없는 오토메이션·라우팅·플러그인 기능은 먼저 DAW에 구현해야 합니다.

코드 작곡은 [Scribbletune/Strudel 비교 실험](COMPOSITION_LANGUAGE_POC.md)을 바탕으로 언어 프로파일과 라이선스 통합 정책을 정합니다. 이후 유한 패턴 → 공통 음표 이벤트 → 트랙/리전 편곡 → 한 번의 Undo 경로를 연결하고, 코드·seed·컴파일러 버전 저장과 수동 편집 후 재생성 정책을 추가합니다. 이번 패스에는 앱 내 코드 실행기를 넣지 않았습니다.

**완료 기준:** 자연어 요청의 대상·범위·단위를 실제 상태와 대조하고, 변경 전후를 확인하며, 한 번의 Undo로 작업 묶음을 되돌립니다. 오래된 상태·재시도·연결 중단으로 중복 편집이 일어나지 않아야 합니다. 작곡 언어는 고정 fixture뿐 아니라 동일 조건의 생성·수정 과제와 사람의 청음에서 검증합니다.

### A. 작업 보존과 반복 사용

- 여러 프로젝트를 구분해 보관하고 다시 여는 프로젝트 관리 기능.
- 브라우저 종료·저장 공간 부족·손상된 파일·중단된 쓰기에서의 복구 흐름.
- 원본 음원과 프로젝트의 장기 보존을 위한 백업·형식 이전 정책.
- 실사용 중 편집 이력의 경계와 복구 경험 검증. 드래그 한 번을 한 번의 실행 취소로 되돌리는 현재 방식을 전체 편집 조작에 일관되게 적용.
- 로컬 저장·프로젝트 파일 가져오기·다시 재생까지 이어지는 실제 브라우저 회귀 테스트.

**완료 기준:** 오디오를 포함한 프로젝트를 저장하고 브라우저를 다시 연 뒤, 클립 위치·원본 오프셋·음표·믹서·효과가 복원되는 것을 지원 환경에서 확인합니다. 저장 실패를 성공으로 표시하지 않으며, 복구할 수 있는 작업과 복구할 수 없는 작업을 구분합니다.

### B. 음악 편집과 연주

- 노트·클립 다중 선택, 일괄 이동·복사, 명확한 선택 범위와 편집 도구.
- 노트 퀀타이즈와 세기 일괄 편집.
- 메트로놈과 녹음 카운트인.
- MIDI 파일 가져오기(Type 0/1 PPQ)는 구현했습니다. [사용법과 지원 범위](MIDI_IMPORT.md). 외부 MIDI 입력, 파일 내보내기와 템포·컨트롤 오토메이션 가져오기는 후속 과제입니다.
- 볼륨·팬·효과 등의 오토메이션 레인과 저장·재생·출력 연결.
- 타임 스트레칭·템포 변경에 대한 오디오 클립의 동작 규칙 확정과 구현.

**완료 기준:** 편집 화면의 변화가 실시간 재생과 WAV 출력에 같은 의미로 반영됩니다. 지원하지 않는 타임 스트레칭·자동화·MIDI 기능을 활성화된 것처럼 보여 주지 않습니다.

### C. 녹음 정확성과 장치 경험

- 수동 ms 정렬에 더해 입력·출력·인코더 지연을 측정하고 정확도를 검증하는 정책.
- 구현된 입력/출력 오류·권한 거부·연결 변경·재적용 경로를 실제 브라우저와 장치에서 검증하고, 브라우저 오디오 중단·긴 녹음의 복구 경험 보완.
- 연결된 장치 선택·소프트웨어 모니터링·프로젝트 레이트의 브라우저별 지원 범위와 실기기 동작 기록. 물리 다중 I/O·동시 다중 입력 녹음은 후속 설계.
- 긴 녹음을 전체 청크와 전체 디코딩 버퍼에만 의존하지 않도록 저장 경로 개선.

**완료 기준:** 알려진 기준 신호를 사용해 녹음 배치 오차를 측정하고 결과와 조건을 기록합니다. 샘플 단위 정렬을 달성하기 전에는 이를 보장한다고 표현하지 않습니다.

### D. 메모리·재생 성능

- 긴 오디오의 부분 읽기·캐싱 또는 스트리밍 경로.
- 파형 분석과 큰 데이터 처리의 Worker 분리 및 확대 수준별 파형 캐시.
- 큰 `.garak` 파일에서 생기는 base64·JSON 메모리 부담 개선.
- 장시간 WAV 출력의 스트리밍 인코딩 또는 단계별 렌더링 방식 검토.
- UI가 바쁠 때와 백그라운드에서 재생 예약이 지연되는 경우 측정. 필요한 경우 AudioWorklet·Worker 등의 예약 구조를 비교.
- 프로젝트 변경 시 그래프 재생성 비용과 효과·동시 음성 수 증가에 따른 비용 측정.

**완료 기준:** 브라우저·CPU·운영체제·샘플레이트·트랙 수·동시 음성·효과 조합을 명시한 벤치마크를 공개합니다. CPU·메모리·끊김·편집 반응을 함께 기록합니다. 측정 전에는 100트랙 또는 200트랙 지원을 보장하지 않습니다.

### E. 배포와 오픈소스 재현성

- 지원 브라우저·운영체제 범위와 실제 확인된 조합 정리.
- 키보드·접근성·다양한 화면 폭에서의 편집 경로 점검.
- 고정된 의존성과 잠금 파일로 개발·테스트·배포 빌드를 재현.
- 공개 소스, 라이선스 고지, 버전별 변경 기록과 알려진 문제 정리.
- 브라우저 기본 노드 기반 엔진을 유지할지, 별도 엔진을 채택할지 성능·기능 근거로 결정. 현재 openDAW나 다른 외부 DAW 엔진의 통합은 이루어지지 않았습니다.

## 2.0: 로컬 네이티브 플러그인

### 목표 구조

React·TypeScript로 만든 작업 화면을 유지하고, 로컬 네이티브 호스트가 외부 악기·효과와 오디오 처리를 담당합니다. 웹 UI를 담는 데스크톱 셸과 네이티브 엔진은 다른 책임이며, 호스트 없이 Electron 포장만 추가하는 것은 이 단계의 완료가 아닙니다.

### 구현할 항목

| 영역 | 필요한 작업 |
| --- | --- |
| 엔진 연결 | 명령·상태 프로토콜, 프로젝트 동기화, 자산 식별, 프로세스 시작·종료·복구 |
| 플러그인 발견 | 설치 경로 스캔, 형식·플랫폼·CPU 호환성 확인, 문제 플러그인 분리 |
| 악기와 효과 | VST3 우선 로딩·MIDI 처리·오디오 버스·효과 체인·멀티 출력 |
| 플러그인 화면 | 원래 네이티브 GUI를 별도 창으로 표시, 창 수명 주기와 스케일 처리 |
| 프로젝트 복원 | 플러그인 식별자·버전·상태·프리셋 저장, 없는 플러그인의 표시·대체 흐름 |
| 타이밍 | 샘플 위치, 템포, 루프, 자동화, 플러그인 지연 보상 |
| 내보내기 | 같은 네이티브 그래프를 이용하는 오프라인 렌더링·스템 출력 |
| 호환성 | OS별 실제 가상악기·효과 조합 검증, 실패 재현과 알려진 문제 관리 |

기존 호스트·DAW 엔진 재사용 여부는 이 단계에서 확정합니다. VST3 지원과 AU·CLAP 지원을 한 기능으로 묶어 가정하지 않고, 선택한 엔진과 플랫폼에서 각각 검증합니다. 플러그인 제작을 지원하는 SDK가 해당 플러그인의 호스팅까지 제공하는지도 구분합니다.

네이티브 호스트를 별도 프로세스로 둔다고 플러그인별 오류 격리가 자동 완성되는 것은 아닙니다. 오디오 엔진 전체가 중단되는 범위와 개별 플러그인만 중단되는 범위를 명시하고, 상태 복원과 사용자 안내를 구현합니다.

## 이후 검토할 서비스 기능

클라우드 프로젝트 보관, 기기 간 동기화, 공유·협업, 원격 렌더링은 현재 제품 기능이 아니며 별도 설계 대상입니다. 정적 웹 페이지를 클라우드에 배포하는 것과 오디오 엔진을 서버에서 실행하는 것을 구분합니다.

사용자 PC에 설치된 상용 가상악기가 서버에서도 자동으로 실행되거나 다른 사용자의 브라우저에 전달되는 것으로 가정하지 않습니다. 현재 로드맵의 우선순위는 로컬 작업의 보존·편집·재생 품질입니다.
