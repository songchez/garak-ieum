# 내장 기타 앰프

가락이음의 `guitar-rig` 디바이스는 입력 모니터링, 오디오 리전 재생, WAV 내보내기에 같은 신호 처리를 사용합니다. 별도 HTML이나 외부 플러그인을 띄우지 않고 기존 React 디바이스 랙, 프로젝트 상태, 실행 취소 기록, 오디오 엔진 안에서 동작합니다.

## 사용 방법

1. **트랙 추가 → 기타 → 생성**을 선택합니다. 기타 앰프가 연결된 오디오 트랙이 생깁니다. 기존 트랙에는 **디바이스 추가 → 기타 앰프**로 추가할 수 있습니다.
2. 디바이스 랙에서 기타 앰프 편집 화면을 엽니다.
3. 실제 기타를 연주하려면 오디오 인터페이스에 기타를 연결하고, 가락이음의 오디오 설정에서 입력·출력 장치를 선택합니다. 소프트웨어 모니터링과 트랙의 입력 모니터링을 켭니다. 트랙을 만들기만 해서는 마이크 권한을 요청하거나 입력을 켜지 않습니다.
4. 프리셋을 선택하거나 노브와 페달 풋스위치를 조절합니다. 편집 화면은 실제 앰프의 신호 순서대로 위에서부터 **프리 · PEDALS** 랙, **앰프 헤드**, 앰프와 스피커 사이의 **FX 루프** 랙, **캐비닛(스피커)·마이크**로 놓이며, 두 랙에 페달을 4칸씩, 랙마다 최대 8개까지 꽂습니다. 왼쪽 이펙터 목록에서 칸으로 끌어 놓거나 눌러서 꽂고(드라이브 계열은 프리 랙, 공간·모듈레이션 계열은 FX 루프 랙 끝, 그 랙이 가득 차면 다른 랙), 빈 칸의 **+ 이펙터 꽂기**를 쓸 수도 있습니다. 칸 머리를 끌어 순서를 바꾸거나 다른 랙으로 옮기고, 복제 버튼이나 목록에서 다시 눌러 같은 페달을 한 대 더(최대 3대, 튜너는 1대) 꽂을 수 있습니다. 입력 모니터링 중에는 헤드폰을 사용하고 인터페이스의 직접 모니터링과 이중으로 듣지 않도록 설정합니다.
5. 지금 톤을 **프리셋 저장**으로 이름을 붙여 저장하면 프리셋 목록의 **내 프리셋**에 들어갑니다. 랙 순서, 같은 페달의 둘째·셋째 사본, 앰프·캐비닛 설정까지 모든 값을 저장합니다. 같은 이름으로 저장하면 덮어쓰고, 내 프리셋을 고른 상태에서 휴지통 버튼으로 지울 수 있습니다(지워도 지금 소리는 그대로). 내 프리셋은 프로젝트 파일이 아니라 이 앱의 로컬 저장소(`garak-ieum:guitar-rig-presets`, 최대 200개)에 보관되어 모든 프로젝트에서 쓸 수 있습니다.
6. 노브와 프리셋 설정은 프로젝트에 저장됩니다. 원본 녹음에는 이펙트를 덮어쓰지 않으므로 녹음 뒤에도 톤을 바꿀 수 있습니다. WAV 내보내기에는 현재 앰프 설정을 적용합니다.

## 신호 처리

신호 순서는 **입력 → 프리 랙 → 앰프 → FX 루프 랙 → 캐비닛 → 출력**이며, 칸 번호(왼쪽 → 오른쪽, 위 → 아래)가 랙 안의 순서입니다. 저장값 `rackSlot0`–`rackSlot17`(페달 8 + 앰프 + 캐비닛 + 페달 8)에 `모듈 코드 + 16 × 사본 번호`를 순서대로 기록합니다(0은 빈 칸, 사본 0–2). 사본 0은 원래 파라미터 이름을, 사본 1·2는 `_2`·`_3`을 붙인 이름(`driveGain_2`)을 써서 이전 프로젝트는 그대로 열립니다. 랙에 없는 모듈은 소리에 영향을 주지 않으며, 캐비닛 뒤에 이펙터가 있던 이전 랙은 FX 루프에 보여 주고, 다음 편집 때 캐비닛 앞으로 저장합니다(그때부터 캐비닛 필터가 그 이펙터에도 걸립니다). 각 모듈과 전체 디바이스를 각각 바이패스할 수 있습니다.

기본 랙은 **컴프 → 오버드라이브 → 앰프 → 캐비닛·마이크 → 코러스 → 딜레이**입니다. 퍼즈·페이저·트레몰로·리버브·튜너는 기본 랙에 들어 있지 않고 꺼진 상태가 기본값이므로, 이전에 저장한 프로젝트는 소리가 그대로입니다. 모듈 코드는 저장 형식이라 바꾸지 않고, 새 모듈은 새 코드를 받습니다.

| 코드 | 모듈 | 조절 항목 (저장 ID · 범위 · 기본값) | 처리 방식 |
| --- | --- | --- | --- |
| 1 | 컴프 (다듬이 Comp) | 서스테인, 어택(ms), 레벨(dB) | 미래 샘플을 기다리지 않는 인과적 엔벌로프 압축 |
| 2 | 오버드라이브 (Green Howler) | 드라이브, 톤, 레벨 | 오버샘플링 비선형 처리와 톤 필터 |
| 3 | 앰프 | Twinline '65(클린) · 청자 Jazz(따뜻한 클린) · Topboost 30(차임) · Plexton 59(크런치) · 옹기 Lead(하이게인), 게인, 베이스, 미들, 트레블, 프레즌스, 마스터 | 프리앰프·톤·출력의 알고리즘 모델 |
| 4 | 캐비닛·마이크 | 장독 1×10 · 소반 1×12 · Blackline 2×12 · Chime 2×12 · Brit 4×12 / DM-75(다이내믹) · 장구 D42(대형 다이내믹) · RB-212(리본) · 달항아리 C8(대형 콘덴서) · Pencil 84(소형 콘덴서), 중앙–가장자리, 가까이–멀리 | 스피커 대역·공진, 고역 지향성·저역 근접 효과를 표현하는 필터 모델 |
| 5 | 코러스 (Blue Ripple) | 속도, 깊이, 믹스 | 변조 지연 |
| 6 | 딜레이 (메아리 Delay) | 시간(ms), 반복, 믹스 | 필터가 포함된 피드백 지연 |
| 7 | 퍼즈 (Bumble Fuzz) | 퍼즈 `fuzzGain` 0–40 dB · 26, 톤 `fuzzTone` 0–1 · 0.45 (500 Hz–5 kHz 로우패스), 레벨 `fuzzLevel` −36–0 dB · −14 | 40 Hz 하이패스 → 강한 비대칭 클리핑(2배 오버샘플링) → 톤 필터 → DC 제거 |
| 8 | 페이저 (Swirl Phase) | 속도 `phaserRate` 0.05–4 Hz · 0.45, 깊이 `phaserDepth` 0–1 · 0.7, 피드백 `phaserFeedback` 0–0.85 · 0.35 | 1차 올패스 6단을 200 Hz–3.2 kHz에서 지수적으로 스윕, 원음과 50:50 합성, 오른쪽 채널은 LFO가 1/4 주기 앞섬 |
| 9 | 트레몰로 (Tide Tremolo) | 속도 `tremoloRate` 0.5–12 Hz · 4.5, 깊이 `tremoloDepth` 0–1 · 0.5, 모양 `tremoloShape` 0–1 · 0 (사인 → 둥근 사각) | LFO로 음량 변조. 깊이 1이면 골에서 무음 |
| 10 | 리버브 (범종 Reverb) | 잔향 `reverbDecay` 0–1 · 0.45, 톤 `reverbTone` 0–1 · 0.5 (1.5–12 kHz 로우패스), 믹스 `reverbMix` 0–0.8 · 0.25 | 플레이트 계열 합성 IR 컨볼루션. 1.7초·4.2초 IR을 잔향 값으로 섞고, 젖은 신호에 180 Hz 하이패스와 톤 필터 적용. 원음은 그대로 통과 |
| 11 | 튜너 (조율 Tuner) | 켜기/끄기 `tunerEnabled` · 0 | 켜면 페달 튜너처럼 출력을 음소거하고 음정을 표시. 끄면 그대로 통과 |

새 모듈은 모두 `<이름>Enabled` 스위치(기본 끔)를 가집니다. 퍼즈만 2배 오버샘플링 지연(네이티브 8프레임)이 있어 켜져 있고 랙에 있을 때만 지연 보정값에 더합니다. 내보내기 꼬리 길이는 랙에 있고 켜진 모듈만 더합니다: 코러스 0.04초, 딜레이 반복 길이, 리버브는 잔향이 0보다 크면 4.45초(0이면 1.95초).

웹 엔진에서 퍼즈·리버브·튜너는 Web Audio 기본 노드(WaveShaper, ConvolverNode 2개, AnalyserNode)로, 페이저·트레몰로는 컴프·코러스와 같은 워크릿 파일의 프로세서로 처리합니다. 페이저·트레몰로 알고리즘([modulation.ts](../src/devices/guitar-rig/modulation.ts))과 리버브 IR 생성기([reverb.ts](../src/devices/guitar-rig/reverb.ts))는 네이티브 코드와 같은 수식·시드를 사용합니다. 리버브 IR은 리버브를 랙에 넣고 켤 때 처음 만들어 쓰지 않는 리버브는 비용이 없습니다. 네이티브 엔진도 리버브가 들릴 때만 컨볼버를 만듭니다.

### 튜너 지원 범위

- **웹(브라우저) 엔진:** 튜너 위치로 들어오는 신호를 AnalyserNode로 받아, 편집 화면이 열려 있고 튜너가 켜져 있을 때만 약 60 ms마다 [pitch-editor 분석](../src/devices/pitch-editor/analysis.ts)과 같은 YIN 방식(누적 평균 정규화 차분, 임계값 0.15, 포물선 보간, 12 kHz로 다운샘플)으로 음정을 찾습니다. 기준음은 A4 = 440 Hz이고 범위는 40–1600 Hz입니다. 페달의 어두운 화면에 음 이름·옥타브·센트 바늘을 표시하고(±3센트 이내면 초록색), 옆 정보 칸에 주파수와 센트 값을 표시합니다. 엔진이 아직 그래프를 만들지 않았으면 “오디오 엔진 대기 중”, 소리가 없으면 “줄을 튕겨 주세요”를 표시합니다. 내보내기용 오프라인 렌더링은 튜너 화면에 연결하지 않습니다.
- **데스크톱(네이티브) 엔진:** 튜너를 켜면 같은 방식으로 출력을 음소거합니다. 네이티브 엔진에서 UI로 분석 데이터를 보내는 경로가 아직 없으므로 음정을 추정하거나 꾸며 내지 않고, 화면에 “데스크톱 엔진에서는 아직 지원되지 않음”을 표시합니다.

장비 이름은 계열을 떠올리게 하는 가락이음 자체 이름이며 실제 제품명·상표가 아닙니다. 저장값 0–2는 기존 Clean/Crunch/Lead, Compact/Open/Stack, Dynamic/Ribbon/Condenser와 같고 3–4가 추가 모델이라 기존 프로젝트의 소리는 바뀌지 않습니다. 캐비닛과 마이크는 **자체 알고리즘에 의한 음색 모델**입니다. 특정 제조사 장비의 회로 복각, 실측 임펄스 응답(IR), Neural Amp Modeler 캡처를 포함하지 않습니다. 마이크 위치·거리는 음색 조절값이며 실제 센티미터 측정치가 아닙니다. UI도 해당 방식으로 표시합니다.

## 프로젝트·자동화 통합

- 디바이스 ID는 `guitar-rig`입니다. 기존 `Device.params: Record<string, number>`에 154개의 수치형 설정(모듈 설정 46개, 둘째·셋째 사본 설정 90개, 랙 칸 18개)을 저장합니다. 프리셋처럼 모든 값을 한 번에 보내는 AI 명령 `effect.add`의 효과당 파라미터 한도는 256개입니다.
- 모든 기본값·범위·옵션은 [definition.ts](../src/devices/guitar-rig/definition.ts)에 정의합니다. UI, 프로젝트 검증, AI 명령 카탈로그가 같은 정의를 사용합니다.
- 기타 앰프의 값은 모두 기존 수치형 디바이스 구조로 저장합니다. 새 모듈이 생기기 전에 저장한 프로젝트에는 새 값이 없으므로 기본값(꺼짐·랙 밖)으로 채웁니다. 현재 프로젝트 스키마 7은 같은 디바이스 체인의 VST3 상태를 함께 보존하며 스키마 1–5를 자동 변환합니다. 새 스키마나 디바이스를 모르는 이전 앱에서는 해당 프로젝트를 열 수 없습니다.
- 자동 저장, `.garak` 파일, 트랙 복제, 전체 바이패스, 디바이스 이동·삭제와 실행 취소에 기존 프로젝트 경로를 사용합니다.
- AI 명령의 `effect.add`, `effect.setParam`, `effect.setEnabled`도 같은 범위 검증을 적용합니다.
- 프리셋 변경은 여러 파라미터를 하나의 프로젝트 편집으로 적용합니다. 노브 드래그는 기존 히스토리 제스처를 사용합니다.

## 오디오 엔진과 지연

데스크톱은 [네이티브 DSP](../native/src/dsp.cpp)의 기타 앰프를 같은 트랙 그래프에 넣습니다. ASIO/WASAPI/Core Audio 입력 모니터링, 녹음한 리전 재생, WAV 내보내기에 같은 C++ 모듈을 사용합니다. 녹음 파일에는 입력 원본을 보존하고, 재생·출력할 때 현재 앰프 설정을 적용합니다. 네이티브 호스트나 효과 처리가 실패하면 오류를 표시합니다.

브라우저 데모는 [effectPreparation.ts](../src/audio/effectPreparation.ts)로 Web Audio/Worklet 프로세서를 준비합니다. 브라우저의 기타 프로젝트에서는 미래 샘플을 기다리지 않는 마스터 컴프를 사용하며 장치 삭제·그래프 교체 시 워크릿과 메시지 포트를 정리합니다. 데스크톱의 마스터는 네이티브 그래프에서 처리합니다. 자체 DSP와 브라우저 내부 구현의 출력이 비트 단위로 같다는 뜻은 아닙니다.

엔진이 표시하는 드라이버의 지연 보고값과 기타 입력부터 헤드폰까지의 실측 왕복 지연은 다릅니다. 실제 연주감은 인터페이스·드라이버·버퍼·플러그인에 영향을 받으므로 장비를 연결한 루프백 측정과 청취 검증이 필요합니다. [네이티브 오디오 구조와 현재 검증 범위](NATIVE_AUDIO.md)

## 에셋 규격

장비 그림은 로고·문구 없는 프롬프트로 Google Gemini에서 생성한 오리지널 일러스트입니다. 흰 배경을 제거하고 캔버스에 맞춘 뒤 WebP로 저장합니다(`src/assets/guitar-rig/`). 이름은 계열을 떠올리게 하는 가락이음 자체 이름이며 실제 제품명·상표·로고를 쓰지 않습니다. 노브 캡만 회전하고 몸체·눈금·텍스트는 고정합니다. 라벨과 값은 이미지에 합성하지 않고 접근 가능한 HTML로 표시합니다.

| --- | --- | --- | --- | --- |
| 앰프 헤드 5종 (`amps/`) | 1200 × 600 | 2:1 | 최대 720 × 360 CSS px | 앰프별 빈 조작 패널 영역(%)에 노브 6개·전원 스위치를 배치 |
| 캐비닛 5종 | 768 × 512 | 3:2 | 384 × 256 CSS px | 캐비닛별 스피커 중심·반지름을 기준으로 마이크 위치 표시 |
| 마이크 5종 (`mics/`) | 480 × 360 | 4:3 | 96 × 72 CSS px | 마이크 선택 옆 사진 |
| 페달 (`pedals/`) | 360 × 600 | 3:5 | 180 × 300 CSS px | 모든 페달이 같은 노브·LED·풋스위치 좌표 사용 |
| 노브 캡 | 128 × 128 | 1:1 | 44 × 44 CSS px | 회전축 `(64, 64)`, 반경 60px |

편집 화면의 앰프 헤드는 세로 배치에 맞춰 가로로 긴 헤드를 CSS로 그립니다. 헤드에는 스피커가 없고(스피커는 아래 캐비닛) 모델마다 토렉스·파이핑·패널·엠블럼 색을 다르게 씁니다. 앰프 그림(amps/*.webp)은 디바이스 랙 요약과 썸네일에 씁니다. 페달은 몸체만 생성하고, 풋스위치와 LED는 고정 좌표에 합성해 클릭 영역과 정확히 맞춥니다. 페달 그림에는 글자를 넣지 않고 이름은 랙 머리와 장비 목록에만 표시합니다. 튜너 페달은 노브가 없고, 그림의 어두운 화면 영역(180×300 기준 left 28, top 48, 134×56 CSS px)에 HTML로 음정을 겹쳐 표시합니다. 앰프 패널 영역, 스피커 좌표와 각 그림의 저장값 대응은 `asset-manifest.json`에 기록합니다.

## 검증 범위

`src/core/guitarRig.test.ts`는 전체 파라미터와 바이패스의 저장·복원, 원본 음원 바이트 보존, 잘못된 파라미터 거절, AI 명령과 실행 취소를 검사합니다. DSP와 오디오 엔진 테스트는 별도로 프로세서 상태·신호 처리·준비 실패·리소스 정리를 검사합니다.

```sh
pnpm test
pnpm build
pnpm mcp:build
pnpm desktop:compile
node scripts/guitar-rig-smoke.mjs
```

브라우저 검증 스크립트에는 Playwright Chromium이 필요합니다. `GARAK_CHROMIUM_EXECUTABLE`로 설치된 Chromium을 지정할 수 있습니다. 이 스크립트는 별도의 브라우저 컨텍스트와 가상 입력을 사용해 새 기타 트랙, 노브·프리셋 실행 취소, 모니터링, 저장 후 복원, 48/96kHz 처리, 마이크 설정에 따른 실제 출력 변화, WAV 생성을 확인합니다. UI와 DSP에 새 런타임 패키지를 추가하지 않았습니다.

자동 테스트는 실제 기타·오디오 인터페이스로 측정한 왕복 지연이나 청취 평가를 대신하지 않습니다.
