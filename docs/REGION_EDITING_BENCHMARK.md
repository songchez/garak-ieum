# Logic Pro 리전 편집 사용성 벤치마크

2026-11-01 · 조사 기준 코드: [`c3203092`](https://github.com/songchez/garak-ieum/tree/c3203092dcc1217b45c7c5d2c9e75c08b1ba470e)

## 1. 목적과 근거의 수준

다음 개발의 우선순위는 **리전 편집의 내용 보존, 정확한 표시, 예측 가능한 손동작**입니다. 선택 → 이동·복사 → 트림·반복 → 부분 편집 → 취소·복구의 작업 흐름을 기준으로 비교합니다. 메트로놈 등 별도 기능보다 이 흐름의 결함을 먼저 정리합니다.

이번 문서는 Apple 공식 설명서 조사와 현재 소스의 대조 결과입니다. **Logic 앱을 직접 조작하거나 가락이음의 변경 후 화면·청음을 검증한 결과는 아닙니다.** 코드에서 확인한 문제와 실제 브라우저에서 확인할 후보를 구별합니다. 구현 상세는 [리전 편집 코드 감사](REGION_EDITING_AUDIT.md), 기존 구현·검증 이력은 [구현 상태](IMPLEMENTATION_STATUS.md)를 함께 봅니다.

| 표기 | 의미 |
|---|---|
| 공식 | 현재 Apple Mac용 설명서에 명시된 동작. 각 항목의 출처를 연결합니다. |
| 코드 | 기준 커밋에서 확인한 구현. 화면에서 직접 재현했다는 뜻은 아닙니다. |
| 제품 기준 | 가락이음이 채택할 품질 기준 또는 설계 제안. Apple의 내부 구현으로 설명하지 않습니다. |
| 실측 필요 | 문서만으로 확정되지 않은 동작. Logic과 가락이음을 같은 조건으로 조작해 기록해야 합니다. |

Apple의 현재 `/mac` 페이지 버전 선택에는 **Logic Pro for Mac 12.3**이 표시됩니다. 이 문서의 비교 대상은 그 Mac용 설명서이며 iPad 제스처와 혼용하지 않습니다. 릴리스 날짜나 모든 사용자의 설치 버전을 뜻하지 않습니다. 과거 `10.7/mac/11.0` 문서는 별도로 표시합니다. 예를 들어 현재 스냅 기본값은 Absolute지만 10.7 설명은 Relative였습니다. [A1][H1]

## 2. 비교할 Logic 설정을 먼저 고정합니다

최소한 다음 설정을 비교 기록에 남깁니다. 사용자 설정 때문에 달라지는 동작을 모두 기본값이라고 부르지 않습니다.

| 설정 | 기본 비교 조건 | 추가 비교 |
|---|---|---|
| 기본 도구 | Pointer | Pencil, Scissors, Marquee, Fade |
| Command 보조 도구 | 할당 도구를 기록 | Marquee를 지정한 경우 |
| Fade/Marquee 클릭 구역 | 끈 상태로 모서리 기준 확인 | 각각 켠 경우와 함께 켠 경우 |
| 한 방향 드래그 제한 | 설정값을 기록 | Shift를 누를 때 제한/해제가 바뀌는 경우 |
| Snap | Smart + Absolute | Beat/Division, Relative, 끔, 정밀 수정키 |
| Drag | Overlap | No Overlap, 이후 X-Fade/Shuffle |
| 프로젝트 | 4/4, 고정 120 BPM, Flex 끔 | 줌·트랙 높이·샘플레이트 변화 |

도구 슬롯과 클릭 구역은 [A7][A8], 축 제한 설정은 [A3]을 기준으로 합니다. Windows 키 대응은 가락이음의 별도 제품 결정입니다. macOS의 ⌃ Control과 ⌘ Command를 모두 Windows Ctrl로 치환하지 않습니다. 웹 브라우저가 선점하는 키는 메뉴·툴바 경로를 함께 제공하고 실제 OS에서 확인합니다.

## 4. 구현 전에 확정할 제품 계약

다음은 Apple 내부 구현 설명이 아니라 가락이음의 설계 방향입니다. 실제 함수·필드명은 구현 PR에서 정합니다.

### 4.1 내용과 보이는 구간

MIDI는 보존된 원본 노트와 리전이 보여주고 재생할 구간을 구별합니다. 트림은 그 창을 바꾸고 음표 삭제는 명시적 편집으로만 수행합니다. 경계에 걸친 노트의 발음·길이, 피아노롤 표시, 복사·분할·결합·퀀타이즈도 같은 구간 규칙을 사용해야 합니다.

오디오는 asset 전체와 `offsetSeconds`부터의 리전 구간을 구별합니다. 파형을 표시할 때 그 구간을 사용하며, 화면에 맞추려고 원본 peaks를 덮어쓰지 않습니다. 같은 파일을 참조하는 다른 리전·복사본은 영향을 받지 않아야 합니다.

이 모델을 바꾸는 PR에는 기존 `.garak` 읽기와 새 형식 왕복이 포함됩니다. 이전의 파괴적 MIDI 트림으로 이미 삭제된 음표를 새 모델이 복원해 준다고 설명하지 않습니다.

### 4.2 제스처 상태

누름에서 원본·선택을 보관하고, 드래그 임계값을 넘으면 미리보기를 시작합니다. 이동·복사·트림·루프는 각각 의도를 표시합니다. 놓을 때 검증된 결과 전체를 한 번 확정합니다. Escape·창 포커스 상실(blur)·포인터 취소는 미리보기와 진행 중 오디션을 정리하고 문서·Redo를 보존합니다. 포인터만 창 경계를 넘는 상황과 blur는 구별합니다.

기존 4px 임계값, 24px 가장자리 영역, 프레임당 10px 자동 스크롤은 **현재 가락이음 값**입니다. Logic의 실측 수치로 취급하지 않습니다. 정지한 포인터에서도 키 변화와 자동 스크롤 때문에 프리뷰가 바뀌어야 하는지 브라우저에서 검증합니다.

### 4.3 수동 루프

최소한 `끔 / 자동 종료점 / 수동 종료점`의 의미를 구분해야 합니다. 모든 소비자—리전 표시, 반복 hit area, 재생, WAV, 저장, 복사, Undo—가 같은 반복 범위를 사용해야 합니다. 기존 `loop: true` 파일은 현재의 연속 반복 의미로 읽습니다.

수동 끝점을 곡의 절대 시각으로 저장할지, 리전 시작 기준 길이로 저장할지는 이동·원본 길이 변경의 실측 결과로 정합니다. `loopLength` 필드 추가만으로 완료라고 판정하지 않습니다.

### 4.4 선택과 부분 편집

리전 ID 집합과 `시작 시간 + 끝 시간 + 트랙 집합`인 부분 선택을 구별합니다. 도구 명령은 둘 중 실제 활성 대상을 사용합니다. 일반 박스 선택이 리전의 일부분을 스쳤다는 이유로 잘라서는 안 됩니다.

혼합 트랙 붙여넣기는 확정 전에 매핑을 계산합니다. 자동 트랙 생성, 전부 거부, 명시적인 일부 허용 중 지원할 정책을 UI와 함께 정하며 조용한 생략은 허용하지 않습니다. Command 보조 도구를 도입할 때 기존 Mod 클릭 사용자와 Windows 대응을 함께 다룹니다.

## 5. 재현 가능한 비교 시나리오

### 공통 자료

120 BPM·4/4 프로젝트에 MIDI 두 트랙과 오디오 두 트랙을 만듭니다. 아래 숫자는 소스 계산을 위한 **0부터 시작하는 beat**이며 UI 마디 번호와 혼용하지 않습니다.

- MIDI A: 시작 4, 길이 8. 내부 0박 짧은 음표, 0.5박에서 2박 지속하는 음표, 7박 음표를 둡니다.
- MIDI B: 시작 `16 + 7/960`, 길이 4. 격자에서 벗어난 이동을 비교합니다.
- 오디오 A: 120 BPM에서 8박인 4초 파일. 앞 2초는 무음, 2.25초에 뚜렷한 타격음이 있습니다.
- 다음 리전을 beat 24에 놓고 프로젝트 끝은 beat 40으로 둡니다. 일부 시나리오에서는 다음 리전을 제거하거나 뮤트합니다.

각 시나리오는 공통 자료의 새 복사본에서 시작하고 해당 행의 변경 조건을 적용합니다. 기록 항목은 `Logic 버전/설정, OS/입력 장치, 입력 순서, 포인터·키 타이밍, 프리뷰, 확정된 데이터, 선택·포커스, Undo/Redo, 들리는 결과`입니다. 자동 검사와 화면/청음 결과를 별도 칸에 기록합니다.

## 7. 기존 문서와의 관계

- [INTERACTION_SPEC](INTERACTION_SPEC.md)의 §7, §8.1, 부록 A에는 제품 제안과 과거 구현 스냅샷이 섞여 있습니다. Relative 기본값, Control=스냅 해제, 일반 다중선택으로서 Command, alias 예약의 실제 적용 여부를 현재 사실로 읽지 않습니다.
- [LOGIC_GAP](LOGIC_GAP.md)는 트랙 UI 중심의 과거 격차표입니다. 새 리전 편집 작업은 이 문서의 RE/Q 번호와 [코드 감사](REGION_EDITING_AUDIT.md)를 기준으로 연결합니다.
- [SHORTCUTS](SHORTCUTS.md)는 현재 동작 안내를 유지합니다. 향후 코드가 바뀌는 PR에서 해당 키맵·도움말·테스트를 같이 갱신합니다.
- 이번 문서 작성은 기능 구현이나 실기기 검증 완료를 의미하지 않습니다. 이전 306개 테스트 통과는 기준 코드의 단위 검증 기록이며, 위 22개 시나리오의 통과 수가 아닙니다.
